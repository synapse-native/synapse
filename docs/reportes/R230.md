# R230 - Respuestas vacias de OpenSyn sin aborto por contrato

**Fecha:** 2026-11-18 | **ME:** r230_opensyn_contratos_mocks | **Commit:** `fa3349f`
**Base:** `8755070` | **Manual:** 7 §6.3, 2 §5.1, 6 §1.1
**Deuda:** R230 del plan maestro (normalizacion de contratos/mocks OpenSyn)

## Problema

`bucle_validacion_detallado` pasaba la respuesta del LLM directamente a
`validar_con_check`, cuyo contrato exige `longitud(codigo) > 0`. Cuando el LLM
devolvia una cadena vacia, el proceso abortaba con
`Assertion failed: Fallo en contrato: requiere` en el C generado, en vez de
devolver un error recuperable. El pipeline multiagente tenia el mismo hueco:
`validar_codigo("")` devolvia falso y `validation_loop_corregir("")` violaba su
propia precondicion.

Los mocks existentes ya usaban codigo invalido no vacio, por lo que el caso de
respuesta vacia no estaba cubierto.

## Cambio

`opensyn/validation_loop.syn`:

- Nueva constante `ERR_RESPUESTA_VACIA`.
- Nueva funcion publica `es_codigo_vacio(codigo: texto) -> booleano` con
  `requiere`/`garantiza`.
- `bucle_validacion_detallado` intercepta la respuesta vacia del intento
  inicial y de cada reintento antes de invocar `validar_con_check`, retornando
  `errores`/`error_mensaje = ERR_RESPUESTA_VACIA` y el numero de intento real.
- Las llamadas a la guarda pasan `_syn_strcpy` porque `texto` se consume al
  pasarse por valor en Synapse; sin la copia se corrompia `codigo_actual`.

`opensyn/pipeline_multiagente.syn`:

- `validation_loop_corregir` acepta cualquier texto en su `requiere` y rechaza
  la cadena vacia tanto en la entrada como en la respuesta del Fixer, antes del
  backend compartido de validacion.
- Cada punto conserva su comentario `cumple Manual X §Y`.

## Limites

- El cliente Ollama reintenta internamente una respuesta vacia; la guarda
  intercepta el resultado final. Los tests verifican los intentos logicos del
  bucle, no el numero de peticiones HTTP.
- El timeout de `test_installer` queda como deuda ambiental separada; no se
  modifico un test existente sin aprobacion.
- El trabajo concurrente de R256 (r241 debugger) obligo a usar un indice git
  temporal aislado para los gates y el commit, sin mezclar sus cambios.
