## 1. Objetivo

Cerrar las 8 fallas preexistentes en la suite de tests FASE 5 (contratos lógicos
`requiere`/`garantiza`), que eran bloqueantes para la Definition of Done de la fase:

- **Issue A:** `requiere: 42` y `requiere: "hola"` no generaban error de compilación
  (Manual 2 §5.1: "Todas las expresiones deben ser booleanas")
- **Issue B:** `requiere: b != 0` con `b=0` (literal) bloqueaba la compilación
  en vez de emitir `assert()` para runtime
- **Issue C:** `main()` retornaba `_rc = principal()` → exit code ≠ 0 en éxito

## 2. Implementación

### 2.1 Type checking de expresiones de contrato (Issue A)

`compilador/verificador_formal.py`:
- `_es_expresion_booleana_valida`: cambió `isinstance(expr, (LiteralNumero,
  LiteralDecimal, LiteralBooleano, LiteralNulo))` → solo `LiteralBooleano`
  retorna `True`. Literales numéricos/decimales/cadena/nulo retornan `False`.
- `_es_expresion_contrato_interna`: agregado `LiteralCadena` al isinstance para
  permitir comparaciones como `s != ""`.

`compilador/semantic_types.py`:
- Nuevo método `_validar_contratos_tipos(def_func)` que itera sobre
  `requiere`/`garantiza` y reporta `ERR_VER_CONTRATO_INVALIDO` cuando
  `_es_expresion_booleana_valida` retorna `False`.

`compilador/semantic_checker.py`:
- `_analizar_funcion` llama `self._validar_contratos_tipos(nodo)` después de
  `_validar_firma_funcion`. Antes el chequeo solo corría en modo `--safe`
  (VerificadorFormal); ahora corre en todos los modos.

### 2.2 Eliminación de evaluación estática (Issue B)

`compilador/semantic_types.py`:
- Removida la llamada a `_verificar_requiere_estatico` en `_inferir_tipo_llamada`
  (antes línea 351-352).
- Removidos los 4 métodos: `_verificar_requiere_estatico`,
  `_evaluar_condicion_requiere`, `_resolver_valor_literal`, `_expr_a_str`.

`compilador/diagnostics.py`:
- Removido `ERR_SEM_CONTRATO_REQUIERE` del enum y de los 5 diccionarios de
  mensajes (es, en, fr, pt, de, it). Código muerto (regla 10).

**Razón de diseño:** Manual 2 §5.1 dice "Se evalúa antes de la primera
instrucción del cuerpo" (runtime). La evaluación estática bloqueaba la
compilación para casos como `dividir(10, 0)` con `requiere: b != 0`, pero los
tests esperan que compile y el `assert()` runtime haga el chequeo.

### 2.3 Exit code de main() (Issue C)

`compilador/generator/generator.py`:
- `_emit_main`: cambiado `int64_t _rc = {principal}();` + `return _rc;` →
  `{principal}();` + `return 0;`. La salida del programa va por stdout;
  el exit code 0 indica éxito, el abort de `assert()` produce exit code ≠ 0.
