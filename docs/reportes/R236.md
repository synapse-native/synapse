# R236 — El compilador nativo resuelve su toolchain C (cierra H-R234-1)

**ME:** r236_toolchain_gcc · **Manual:** 9 §6.2 / §7 · **Cierra:** H-R234-1 (ALTO)

## Problema

`dist/bin/synapse.exe` emitía el literal `gcc` en el comando de compilación y dependía
del PATH del usuario. En una máquina limpia sin MinGW configurado, `synapse check`
funcionaba pero compilar fallaba (`"gcc" no se reconoce...` → `ERROR: GCC fallo con
codigo 1`), aunque el toolchain estuviera junto al binario o en el árbol.

## Cambio (`nucleo/principal.syn`)

Antes de invocar `gcc`, el compilador resuelve la ruta del toolchain:

1. `SYNAPSE_GCC` (entorno) — precedencia explícita.
2. `gcc.exe` junto al binario.
3. `tools\mingw64\bin\gcc.exe` · `mingw64\bin\gcc.exe`.
4. `..\toolchain_gcc12\mingw64\bin\gcc.exe` (instalador) y
   `..\..\toolchain_gcc12\mingw64\bin\gcc.exe` (checkout `dist/bin`).
5. `gcc` del PATH (último recurso, comportamiento histórico).

El directorio resuelto se antepone al PATH del proceso hijo (una sola vez, sin
duplicar) y el comando sigue invocando `gcc` **sin comillas**.

Nota de implementación: el primer intento citó el ejecutable resuelto entre comillas
en el primer token (`"C:\...\gcc.exe" -O2 ... -I"." "synapse_unity.c"`). `cmd.exe`
entonces no resolvía la ruta (`El sistema no puede encontrar la ruta especificada.`)
aunque el mismo comando funcionara desde otro proceso; se descartó y se ajustó el
PATH del hijo, que además cubre `as`/`ld`/DLLs de MinGW.

buscadas tiene toolchain (VM realmente limpia), el último recurso sigue siendo el `gcc`
del PATH. Empaquetarlo en el setup queda como seguimiento de R234 (paso 2).
