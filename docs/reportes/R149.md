## 3. HALLAZGOS DETALLADOS

### 🔴 B1 — Fuga de memoria masiva en `synapse_rt.c` (conversiones numéricas → texto)

**Ubicación:** `synapse_rt.c:50-76` (`texto_a_entero` ok; `decimal_a_texto` y `entero_a_texto` rotas).

```c
CadenaSegura entero_a_texto(int64_t n) {
    ...
    char* data = (char*)malloc(len + 1);   // ← malloc crudo
    ...
    return (CadenaSegura){ .longitud = len, .datos = data };
}
```

El contrato RAII del repo (Manual 2 §4.1/§9.1, comentario en `memory.c:457`: "todo CadenaSegura es pool_alloc, RAII libera con pool_free") hace que el código generado libere con `_syn_texto_liberar(s)` → `pool_free(s.datos)`. Pero `pool_free` solo libera (a) punteros dentro del pool/slabs y (b) punteros **registrados** en `_g_extra_ptrs[]` (registrados SOLO por `pool_alloc`). Un `malloc` crudo **no está registrado** → `pool_free` es un **no-op silencioso** → fuga en cada conversión.

**Impacto:** cualquier programa que convierta números a texto en un bucle (logs, contadores, serialización JSON, el propio OpenSyn que imprime `entero_a_texto(...)` constantemente) pierde memoria linealmente. `decimal_a_texto` idéntico. Además `memory.c:462` (`_syn_recibir_como_texto` con `recv` sin timeout) hereda el patrón de red sin plazo que ya se corrigió en `ollama.c` (H-R140).

**Corrección:** usar `pool_alloc(len + 1)` en ambas funciones (verificado: probe de control estable en 4.4 MB con 60M iteraciones). Mismo patrón correcto ya existe en `runtime/core/modelo.c` y en el fix H-F29-T5b.

**Prioridad:** bloqueante. Es exactamente la clase de bug que el Manual 9 §9.5 (auditoría con sanitizadores) existe para prevenir; ASan no corre en este toolchain TDM (no hay `-lasan`), por eso sobrevivió.

### 🔴 B2 — `opensyn/principal.syn` no compila desde `140f39b5` (2026-09-12)

**Ubicación:** `opensyn/principal.syn:920-924` (`ejecutar_tool`, rama `leer`).

El commit `140f39b5` ("fix(audit): auditoria completa OpenSyn — 16 bugs…") introdujo el bloqueo de rutas `~` así:

```syn
            sino:                                          // 921
            si strstr_f(arg, "..") >= 0 o ... :            // 922  ← mismo nivel que 'sino:'
                res = "[TOOL_ERROR] ruta no permitida..."  // 923
                sino:                                      // 924
```

El `si` interno quedó al mismo nivel que el `sino:` (que quedó vacío/huérfano). El parser S1 exige cuerpo indentado tras `sino:` → `Se esperaba INDENT` ×2 (verificado con probe mínimo). La intención obvia era:

```syn
            sino:
                si strstr_f(arg, "..") >= 0 o strstr_f(arg, ":") >= 0 o subcadena(arg, 0, 1) == "~":
                    res = "[TOOL_ERROR] ruta no permitida (usa rutas dentro del repo)"
                    sino:
                        ruta = concat(cwd_act, "/")
                        ...
```

**Impacto:**
1. No se puede regenerar `opensyn.exe` desde fuente.
2. `dist/bin/opensyn.exe` es del **Sep 11 22:28** — STALE: el producto instalado no contiene los fixes de R146 (Sep 13) ni los ME-11..15 (`081eccb`, `a840af8`: flags `--junit/--coverage/--json`, `ejecutar_lint()`, `generar_codigo_ia()` real). Contradice la lección R146 ("producto instalado = producto validado").
3. **Ningún workflow compila `opensyn/principal.syn`** (verificado en los 6 workflows): el gate de CI no puede detectar esta regresión. R141/R142 documentan builds manuales del agente, no hay receta reproducible.

**Corrección:** reindentar el bloque (fix de 4 líneas) + añadir a CI un paso `python main.py opensyn/principal.syn -o dist/bin/opensyn.exe` con verificación de timestamp.

### 🔴 B3 — 5 módulos de `std/` no compilan: firmas multilínea no soportadas por el parser S1

**Módulos afectados:** `std/llvm.syn`, `std/wasm.syn`, `std/proof_bridge.syn`, `std/surface_code.syn`, `std/dist_orchestrator.syn` (más `nucleo/llvm_backend.syn`, `nucleo/wasm_backend.syn`, `nucleo/optimizador_ia.syn`, `opensyn/architect_det.syn` si se compilaran por S1).

```syn
externo funcion BuildCallProgram(ctx: puntero, nombre_modulo: texto,
    valor: entero) -> texto
```

El parser (Python y espejo nativo) no consume el salto de línea dentro de la lista de parámetros: `Se esperaba RPAREN, se encontró COLON` (y variantes `IDENTIFICADOR`/`INDENT`). Verificado con probe mínimo: una `funcion` con parámetros en 2 líneas **nunca** compila, en ninguna variante.

**Impacto:** todo `importar std.llvm|std.wasm|std.proof_bridge|std.surface_code|std.dist_orchestrator` aborta la compilación. La fase F7 del roadmap ("backend LLVM/WASM usable desde Synapse") está inaccesible por el frontend. `tests/unit/test_rag_file_finder.py` y `tests/opensyn/test_rag.py` indexan estos módulos como catálogo (la herramienta de búsqueda de archivos los anuncia), pero ningún usuario puede importarlos.

**Corrección (2 opciones):** (a) soportar continuation de firma multilínea en `compilador/parser_declarations.py` + espejo `nucleo/parser_declaraciones.syn` (paridad), o (b) reescribir las firmas de los 5 módulos a una línea. La (a) es la correcta según Manual 2 (la EBNF no prohíbe saltos dentro de la lista de parámetros) pero toca el compilador; la (b) es mecánica y segura.

### 🔴 B4 — `std/tiempo.syn` declara símbolos C inexistentes

**Ubicación:** `std/tiempo.syn:11-12`.

```syn
externo funcion _syn_ahora_ms() -> entero
externo funcion _syn_dormir_ms(ms: entero) -> nulo
```

`runtime/core/tiempo.c` implementa `_syn_timestamp_ms()`, `_syn_tiempo_*`… pero **ni** `_syn_ahora_ms` **ni** `_syn_dormir_ms`. Verificado con link real: `undefined reference` ×2. Los wrappers `ahora_ms()`/`dormir_ms()` del propio módulo y todo usuario de `std.tiempo` fallan al enlazar. **El runtime provee la primitiva correcta** (`_syn_timestamp_ms`) — el binding está mal escrito.

**Impacto:** roto para todo el ecosistema: `std/http.syn`, `opensyn/memoria_persistente_cifrada.syn`, `opensyn/pipeline_multiagente.syn`, `opensyn/router.syn`, `opensyn/verificacion_aot.syn`, `tests/smoke_tensor.syn`, `tests/smoke_tiempo.syn`. (Que `tests/opensyn` esté verde confirma que los tests Python no compilan estos módulos — blind spot del gate.)

**Corrección:** cambiar el binding a `retornar _syn_timestamp_ms()` y añadir `_syn_dormir_ms` en `tiempo.c` (`Sleep(ms)` / `nanosleep`), o apuntar `dormir_ms` a una nueva primitiva. NOTA: la fuente del fix puede estar ya en el WIP del otro agente (`plan_ME_f32_5b_fixes_ffi.md`); coordinar en bitácora antes de actuar.

### 🟠 M1 — `synapse_llvm.c` / `synapse_wasm.c` nunca se enlazan (cable suelto)

Implementan **todas** las 61 externas de `std/llvm.syn` y `std/wasm.syn` (verificado: `LLVMContextCreate` en `synapse_llvm.c`, `WasmModuleCreate` en `synapse_wasm.c`). Pero:
- `pipeline.py` `_RT_FUENTES` = `synapse_rt.c` + `runtime/core/*.c` + tweetnacl + sqlite3 (+ quantum/federated/IA): **no incluye** ninguno de los dos.
- `tests/conftest.py` `_RT_OBJ_DEFS`: ídem.
- Ningún `#include` de sus headers en el runtime; ningún test los enlaza.

Consecuencia: aunque se arregle B3, `importar std.llvm` seguiría fallando al link. Además `cli.py --target llvm/wasm` usa el generador **Python** (`compilador/llvm_ir_generator.py`/`wat_generator.py`), no estos backends C — dos arquitecturas de backend paralelas sin conectar entre sí.

**Corrección:** decidir cuál backend es canónico; si el C, añadir `synapse_llvm.c`/`synapse_wasm.c` a `_RT_FUENTES` + `conftest` (el auto-link por glob de `runtime/core/` no los cubre porque están en la raíz).

## 4. CAUSA RAÍZ COMÚN

1. **El gate de CI no compila los artefactos de usuario final.** B2 (OpenSyn), B3 (std rotos), B4 (std.tiempo) sobrevivieron porque los 2998 tests nunca enlazan `opensyn/principal.syn` ni un programa que importe cada `std.*`. El gate existe (`auditoria/verificar_alineacion.py`, MTO, MTS) pero es de trazabilidad, no de compilabilidad. Recomendación: un oráculo "compile matrix" que genere un programa mínimo por cada `std.*` y compile `opensyn/principal.syn` + `nucleo/lsp_v3.syn` en cada push (presupuesto: ~10 compila-cortos en paralelo).
2. **La salida feliz de los stubs.** M3/M4 imprimen éxito sin hacer nada — viola el espíritu de "cero deuda sin seguimiento". Marcarlos como no-implementado (rc≠0) hasta que existan.
