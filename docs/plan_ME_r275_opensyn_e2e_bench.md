# Plan ME r275_opensyn_e2e_bench

**Fase del roadmap:** Frente H (release industrial), Ola H1.
**Micro-entregable:** `r275_opensyn_e2e_bench`.
**Depende de:** `r274_gates_independientes` (CERRADO), `r273_installer_modelo_grande` (CERRADO).
**Manuales:** Manual 9 §6.2; Manual 1 §7.4.

---\n\nrequisito: Manual 9 §6.2\ntexto: "Integración E2E OpenSyn + Syquex: el agente OpenSyn debe generar código Syquex válido, compilarlo y ejecutarlo en un bucle de hasta 3 intentos, con validación automática usando el flag --check, y reportar tasas de éxito y fallo. El benchmark debe medir latencia, tasa de éxito y confirmar que el sellado de determinismo se mantiene a través del pipeline."\nimplementacion: 1. Crear suite de benchmark E2E en `tests/integration/test_opensyn_e2e_bench.py` que: ejecute OpenSyn sobre código Python de muestra, transpile el resultado a Syquex, compile el código Syquex con `synapse build --skip-test`, ejecute el binario resultante, y valide la salida esperada usando `--check`. 2. Integrar el flag `--check` / `--no-emit` en el CLI de Synapse (subfase 26.1) para que el benchmark pueda validar sintaxis y semántica sin generar salida. 3. Implementar el bucle de validación automática de hasta 3 intentos: si la primera ejecución falla, corregir y reintentar; si la segunda falla, corregir y reintentar una última vez. 4. Medir y reportar: latencia total por ciclo, tasa de éxito (éxitos sobre total de ciclos), tasa de fallo (fallos sobre total), y confirmar que el grafo de conocimiento y el sellado de determinismo se mantienen a través del pipeline. 5. Los oráculos de gate (de r274) deben seguir pasando (contrastar 3/3 PASS) después de la integración E2E, confirmando que la extracción de gates no rompió determinismo. noraculo: auditoria/oraculos/oraculo_r275_opensyn_e2e_bench.py con estas banderas: `--construir` (lanza `build.py --skip-test` y compara S2==S3, igual que r274), `--sellar` (escribe `synapse_e2e_stage2.stamp` con el hash de la fuente sólo si la verificación E2E pasó), `--estricto` (además de S2==S3, exige que el binario de prueba y `dist/bin/synapse.exe` coincidan con la etapa E2E), `--mutar` (aplica una mutación al código Python de entrada y verifica que el oracle siga pasando; si falla, el gate es frágil y debe reportarse), `--e2e` (ejecuta el benchmark completo y reporta latencia, tasa de éxito/fallo).\n\n criterio_cierre: `contrastar --plan docs/plan_ME_r275_opensyn_e2e_bench.md` → 3/3 PASS (requisito, implementacion, oraculo). `alinelacion.py --leer --me r275_opensyn_e2e_bench` → sin brechas. `alinelacion.py --nuevo --me r275_opensyn_e2e_bench` → expediente sellado. `verificar_alineacion.py` → 0 brechas. Los oráculos pasan en modo release con `SYNAPSE_BUILD_MODE=release` RC=0. CI ejecuta los oráculos como pasos independientes sin bandera `--sin-oraculos` y RC=0. El benchmark E2E confirma tasa de éxito > 95% en 3 intentos máximos. Romper el sello (editar `nucleo/principal.syn` sin actualizar el stamp) hace fallar `--estricto` y el gate correspondiente.\n\n producción_modificada: Cada archivo `.c`, `.h`, `.py`, `.syn`, `.syq` nuevo o modificado que introduzca un benchmark debe llevar el comentario: `// cumple Manual 9 §6.2 // cumple Manual 1 §7.4`
